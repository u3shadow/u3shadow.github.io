Wi-Fi 场景规则生成与执行

把音量、亮度、蓝牙等场景配置从表单升级为自然语言。重点不是做一个聊天壳，而是让输入分流、结构化规则、持久化和环境触发形成闭环。

查看源码阅读重构实录 →

项目介绍

最初的工具通过表单选择 Wi-Fi 及设备动作。重构后，用户可以用一句自然语言描述场景，由模型生成可解析的规则，再由本地执行链处理。

以下实现说明以 2026-04-22 发布的重构文章为依据，不代表仓库的最新状态。首页设备界面是概念展示，不作为日志分析或性能诊断已实现的证据。

实际应用截图

已实现的核心能力

  • 接收文本输入并区分普通聊天与指令聊天。
  • 为不同业务链维护独立上下文与 prompt。
  • 从模型回复解析结构化 JSON 规则。
  • 使用 Room 保存规则，支持重启后读取。
  • 根据 Wi-Fi 变化查询、去重并执行规则，再更新界面。
  • 通过独立能力说明 prompt 限定普通聊天的产品边界。

技术架构

flowchart TD
  UI[MainActivity 输入与环境事件] --> VM[ChatViewModel]
  VM --> Classifier[InputClassifier]
  Classifier --> Normal[NormalChatContextManager]
  Classifier --> Command[CommandChatContextManager]
  Normal --> Prompt[PromptBuilder]
  Command --> Prompt
  Prompt --> Model[模型流式回复]
  Model --> Parse[解析结构化规则]
  Parse --> Repo[RuleRepo / Room]
  UI --> Engine[RuleEngine.run ssid]
  Engine --> Repo
  Engine --> Executor[ActionExecutor]
  Executor --> Result[环境状态与执行反馈]

自然语言规则生成流程

输入需求 → 输入分类 → 指令上下文与 prompt → 流式回复 → JSON 提取与解析 → 构造 Action → 保存规则。模型输出不是执行完成的证明，规则执行由本地链路承担。

例如，原文使用连接公司 Wi-Fi 后静音的场景，规则包含 trigger、operation 和 params。这里不增加原文没有证明的 RAG 或多工具规划能力。

输入分类与上下文管理

InputClassifier 使用规则将输入分流；普通聊天和指令聊天分别由 NormalChatContextManager 与 CommandChatContextManager 维护。原文记录的窗口分别为最近 10 条普通消息和 6 条指令相关消息。

拆分上下文是为了避免日常聊天污染规则 prompt，也使两种交互可以分别演进。当前分类仍是简单规则，不包装成已训练的意图识别模型。

RuleEngine 执行机制

MainActivity 获取当前 SSID 后调用 RuleEngine.run(ssid)。引擎从仓库读取匹配规则、去重并执行，再通过 updateEnvFromRuleResult 与 onRuleRunResult 同步状态。

将运行引擎独立出来，使执行不再依赖用户点击发送消息。设备权限和系统限制仍需结合实际 Android 环境验证。

Room 持久化设计

RuleRepo.init(context) 通过 Room.databaseBuilder 创建 rule_store.db。addRule(action) 调用 DAO 的 upsert，getRules(ssid) 按触发条件读取并转换为 Action。

这让规则不再只是内存状态。原文章未展示数据库迁移策略、压力测试或大规模数据指标，因此不作对应成果声明。

当前局限与后续计划

  • 规则编辑、删除和覆盖策略的 UI，列为后续完善方向。
  • 输入分类需要更细粒度设计。
  • 日志与可观测性需要系统化建设。
  • 消息模式建模和更多系统工具模块，属于后续扩展。
